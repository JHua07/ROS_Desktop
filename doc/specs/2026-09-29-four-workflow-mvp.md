# Four-workflow MVP design (2026-09-29)

The user wants an operable, verifiable graph/echo/launch/bag loop, not packaging or a redesign. This extends the existing daemon graph bridge, not replaces it. Browser mode must render with native actions disabled and an explanation.

## IPC and ownership contract

The root agent owns `src-tauri/src/lib.rs`, `modules/mod.rs`, `modules/process.rs`, `modules/platform.rs`, `modules/environment.rs`, `frontend/src/App.tsx`, `frontend/src/styles.css`, shared frontend `modules/process/index.ts`, and documents. Feature workers own only new feature-specific Rust and React files. The root registers commands and integrates panels.

Existing `environment_status` and `ros_graph_snapshot` shapes stay intact. New command names: `start_topic_echo {topic}`, `start_launch {target, arguments}`, `start_bag {topics, output}`, `stop_ros_process {kind}`. One active process per kind, kinds `topic_echo|launch|bag`; distinct kinds may coexist. Starts return `{session_id,kind,state}`. Duplicate starts reject with `{code:"already_running",message}`. All new command failures serialize as `{code,message}`; no shell string is composed from input. Missing environment returns `environment_unavailable`. A stop when idle returns `not_running`; repeated stop while stopping is idempotent. App shutdown requests stop for all and waits boundedly before forced cleanup.

All process events use `ros-process-event`: `{session_id,kind,state,stream?,line?,exit_code?,error?}`, state `starting|running|stopping|stopped|failed`, stream `stdout|stderr`. Each stream is read separately. Ordered output per stream is retained until its reader EOF; terminal event is emitted after both readers finish. Natural exit code zero is stopped; nonzero is failed unless stop was requested; stopping records exit status and remains stopped if graceful termination succeeds; a forced termination reports `failed` with an incomplete-output warning. The UI retains at most 500 recent lines per feature and filters by session ID; Rust transports lines rather than holding an unbounded log. Stop signals are platform-specific: Unix SIGINT to the managed process group, Windows CTRL_C from an isolated helper attached to the child console (helper failure is surfaced), with bounded grace and forced termination fallback. A Windows CLI smoke confirmed `metadata.yaml` on graceful bag stop; Tauri IPC/GUI end-to-end validation remains outstanding.

Topic echo: absolute ROS topic selected from current graph list, direct argv `ros2 topic echo <topic>`; launch: workspace-contained canonical launch file `.launch.py|.launch.xml|.launch.yaml` selected by a bounded workspace scan, direct argv `ros2 launch <file> [name:=value...]`; argument names restricted to ROS-style identifiers and values reject control characters, with no shell. Bag: selected graph topic names, output directory path with existing parent; reject an existing target (never overwrite), direct argv `ros2 bag record -o <output> <topics...>`. The output parent is not created implicitly. Feature builders validate again in Rust; UI validation alone is insufficient. The Pixi shell-hook environment captured once at startup supplies all three commands. On Windows, managed commands use unbuffered Pixi `python.exe -u Library/bin/ros2-script.py` instead of the `ros2.exe` wrapper so console interrupt reaches the CLI process and echo lines appear promptly. Graph remains daemon XML-RPC only.

## Verification

Focused builder/validation and manager lifecycle tests; final frontend typecheck/build and dist, cargo fmt/test/check, GUI `pixi run` scan. With ROS available, exercise each start/output/stop and invalid/duplicate path, using a generated workspace-local launch fixture and temporary bag output, cleaning only those test artifacts. Clearly separate unavailable runtime checks from passing compile/unit tests.
